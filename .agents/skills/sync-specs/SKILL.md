# 仕様書同期・監査スキル (sync-specs)

このスキルは、Audio Effector リポジトリの **実コード（`AudioEffector/`）** と **設計仕様書（`設計/`）** の乖離を検出し、GitHub Wiki の `仕様書同期・メンテナンスルール` に基づいて仕様書を最新・スリムな状態へ同期するための手順を定義します。

---

## 適用モード

ユーザーからの依頼内容に応じて以下の 3 モードを使い分けます。

1. **差分ベース同期モード**: 特定の Issue 番号・PR 番号・コミット範囲（例: `HEAD~20..HEAD` や直近マージ分）を指定された場合。変更コードに紐づく仕様書を `tools/check_spec_sync.py` で抽出し、該当仕様書のみを実コードへ同期する。
2. **対象指定同期モード**: 特定の画面・機能・仕様書ファイル（例: 「最近再生した曲UI仕様書」「再生キュー関連」）を指定された場合。対象機能の全レイヤーのコードを読み込み、対応仕様書を精査・更新する。
3. **全体監査（Audit）モード**: `設計/` 全体またはカテゴリ単位（画面設計／機能仕様／詳細設計／アーキテクチャ等）の棚卸しを依頼された場合。乖離箇所・重複ファイル・リンク切れ・`設計/spec_map.json` の整合性を網羅的に調査し、優先度付きレポートまたは一括修正を行う。

---

## ワークフロー手順

### Step 1: ルール・対象範囲の確認

1. **基準ルールの確認**:
   - GitHub Wiki の `仕様書同期・メンテナンスルール`（Single Source of Truth、「書くこと／書かないこと」、正本ドキュメント配置原則）を前提とします。
   - UI 仕様書を更新する場合は `.agents/rules/ui_spec_rules.md` および `設計/デザインシステム/01_デザイントークン仕様書.md` も参照します。
2. **対象仕様書の特定**:
   - まずは `spec_map.json` 自体の健全性を検証します：
     ```powershell
     python tools/check_spec_sync.py --validate
     ```
   - 差分ベース同期の場合は対象範囲のファイルを抽出し、逆引きします：
     ```powershell
     # 例: 指定範囲の変更ファイルを取得して仕様書を逆引き
     $files = git -c core.quotepath=false diff --name-only <from>..<to>
     python tools/check_spec_sync.py --files $files
     ```
   - 全体監査の場合は以下も併せて確認します：
     - `設計/` 配下の重複ファイル（例: `* (1).md` 等のコピー残骸）
     - `設計/index.md`・`設計/画面設計/index.md`・`設計/toc.yml` と実ファイル一覧の不一致・リンク切れ
     - `設計/spec_map.json` に未登録の `AudioEffector/` 新規画面・新規機能ファイル

---

### Step 2: 実コードと仕様書の突合

対象となる仕様書と、それに紐づく実コード（`Views/*.xaml`, `Views/*.xaml.cs`, `ViewModels/*.cs`, `Application/`, `Domain/`, `Infrastructure/`）を必ず**両方読み込んで照合**します。

以下の観点で乖離を洗い出します：
1. **UI・レイアウト・インタラクション**: ペイン構成、ツールバー、ボタン、検索・ソート、コンテキストメニュー、ダブルクリック、キーボードショートカット、空状態表示、使用しているテーマブラシ（`DynamicResource`）。
2. **機能仕様・振る舞い**: 記録・発火タイミング、上限件数、重複制御、フォールバック挙動、エラーハンドリング、設定項目。
3. **データ・永続化・I/F**: 保存先ファイルパス・JSON スキーマ・エンティティの役割、リポジトリ・サービスの責務と境界。
4. **状態遷移・ナビゲーション**: 画面遷移トリガー、戻り先、他画面・再生キュー・ライブラリとの連携。

---

### Step 3: 「書くこと／書かないこと」基準による差分分類

検出した乖離を以下の 4 区分に分類し、**安易にコードをそのまま書き写して肥大化させない**ようにします。

| 区分 | 内容 | アクション |
| :--- | :--- | :--- |
| **A. 仕様ズレ（最優先）** | 実コードの挙動・UI・保存形式と矛盾する誤った記述 | 実コード（または意図した仕様）に合わせて修正。実装側のバグが疑われる場合は仕様書を無理に合わせずユーザーへ確認する |
| **B. 重要な仕様の記載漏れ** | 新規追加された画面要素・機能・永続化形式・制約が未記載 | 正本となる仕様書（例: 画面単位なら `画面設計/<画面名>/*UI仕様書.md`）へ簡潔に追記 |
| **C. 陳腐化した過剰詳細** | 全プロパティ一覧・全メソッドシグネチャ・実装内部の細かなフィールド名など、コード／XML コメント／DocFX に任せるべき情報 | 羅列を削って「責務・設計意図・契約・制約」へ要約し、必要に応じて実コードファイルへのリンクへ置換 |
| **D. 重複記述・孤立ファイル** | 複数ドキュメントへの同一仕様のコピペ、`(1).md` 等の重複ファイル、リンク切れ | 正本 1 箇所へ集約し、他ドキュメントからは相対リンク参照のみにする（ファイル削除を伴う場合は影響リンクを確認） |

> **重要**: 実装と仕様書に食い違いがある場合、「実装が正しい（仕様書が古い）」のか「仕様書が正しい（実装にバグ・未実装がある）」のかを必ず判別してください。未実装項目や判断に迷う仕様差異は勝手に書き換えず、ユーザーへ確認するか仕様書内に注記（または後続 Issue 化提案）を行います。

---

### Step 4: 仕様書およびインデックス・マップの更新

1. 正本仕様書を更新します（UI 仕様書の場合は `.agents/rules/ui_spec_rules.md` に準拠）。
2. 関連する他ドキュメントから重複記載を整理し、正本への相対リンクに統一します。
3. 完全に新しい画面・独立機能カテゴリの新設、または既存仕様書の統廃合・リネームが発生した場合のみ、以下も漏れなく同期します（通常の仕様記述修正や既存機能への補助クラス追加では `spec_map.json` の更新は不要、Wiki 側へ個別対応表は転記しません）：
   - `設計/spec_map.json`（ワイルドカード単位で維持）
   - `設計/index.md` / `設計/画面設計/index.md` / `設計/toc.yml`（該当する場合）

---

### Step 5: 検証とコミット

1. **自動検証の実行**:
   ```powershell
   # spec_map.json 内の全仕様書パスの実在検証
   python tools/check_spec_sync.py --validate
   ```
   - 更新した Markdown ファイル内の相対リンク先ファイルが実在することを確認します。
   - 不要ファイルや一時ファイルが混入していないことを `git status` で確認します。
2. **コミット（粒度分割の厳守）**:
   - `.agents/rules/git_operation_rules.md` に従い、`docs: 📝` プレフィックスでカテゴリ・画面単位に分かりやすくコミットします（Issue 番号がある場合は `#<Issue番号>` を付与）。
   - 例: `docs: 📝 #105 最近再生した曲UI仕様書を現行実装へ同期する`
   - 監査のみ依頼された場合（編集指示がない場合）は、ファイルを変更せず乖離レポートと優先対応案をユーザーへ提示します。

---

## 完了報告に含める内容

1. **同期・監査の対象範囲**（モード、対象ファイル／コミット範囲）
2. **検出した乖離と対応結果のサマリー**（A: 仕様ズレ / B: 記載漏れ / C: 過剰詳細のスリム化 / D: 重複・リンク整理）
3. **判断が必要な差異・後続 Issue 化候補**（実装側の未実装やバグが疑われる項目があれば明記）
4. **`check_spec_sync.py --validate` の検証結果**
