# IssueおよびPull Request (PR) 作成ルール

本プロジェクトにおけるIssueとPull Requestの作成基準、および記載すべき内容についてのルールを定めます。
これを守ることで、開発の意図や変更内容が後からでも正確に追跡できるようになります。

---

## 1. Issueの作成ルール

作業（機能追加、バグ修正、リファクタリングなど）を開始する際は、必ず事前にIssueを作成してください。

### Issueの必須項目
Issueの本文には以下の項目を含めるようにしてください。

1. **概要 / 背景 (Background)**
   - なぜこのIssueが必要なのか、現状のどのような課題を解決するのかを記載します。
2. **目的 (Objective)**
   - このIssueで最終的に達成したいゴールを簡潔に記載します。
3. **提案される変更内容 (Proposed Changes)**
   - どのようなアプローチで解決するか、変更する予定の機能やファイルなどを記載します。
4. **期待される動作 (Expected Behavior)**
   - 実装後、ユーザーやシステムがどのように動作するのが正しいかを記載します。

### Issue作成時の注意点
- タイトルは作業内容がひと目で分かる簡潔なものにしてください。（例: `ログ出力機能の追加`, `再生時のノイズバグ修正`）
- 複雑な機能の場合は、タスクをチェックボックス（`- [ ]`）で分割して記載すると進行が分かりやすくなります。

---

## 2. Pull Request (PR) の作成ルール

作業が完了し、`develop` ブランチへマージする際はPull Requestを作成します。

### Pull Requestの必須項目
PRの説明（Description）には以下の項目を含めるようにしてください。

1. **関連Issueの紐付け**
   - 本文の先頭に `Closes #<Issue番号>` を記載し、マージ時にIssueが自動的にクローズされるようにします。
2. **概要 (Overview)**
   - このPRで何を行ったかの全体像を記載します。
3. **対応内容 (Changes Made)**
   - 実際に変更・追加した内容を具体的にリストアップします。
   - （例: `NLogパッケージの追加`, `App.xaml.csに例外ログ処理を追加`）
4. **確認事項 (Checklist)**
   - PR作成者自身が確認した項目をチェックボックスで記載します。
   - 例:
     - [x] ビルドが正常に通ること
     - [x] デバッグ出力にログが表示されること
     - [x] 既存のテストがパスすること

### PR作成時の注意点
- マージ先（Baseブランチ）は必ず **`develop`** に指定してください。（デフォルトが `main` になる場合があるため注意が必要です）
- レビュアーが変更内容を把握しやすいよう、PRの粒度が大きくなりすぎないように心がけてください。大きすぎる場合は複数のPRに分割することを検討してください。
