# Git操作ルール

本プロジェクト（Audio Effector）における Git 操作の統一ルールを定めます。

> **参考**: [Gitのコミットメッセージの書き方（2023年ver.）](https://zenn.dev/itosho/articles/git-commit-message-2023)

---

## 1. コミットメッセージ

### 1.1 フォーマット

[Semantic Commit Message](https://gist.github.com/joshbuchea/6f47e86d2510bce28f8e7f42ae84c716) を採用します。

```
<Type>: <Emoji> #<Issue Number> <Subject>
```

- **Type** と **Subject** は **必須**
- **Issue Number** は **強く推奨**（Issue がある場合は必ず紐付ける）
- **Emoji** は **任意**

#### 例

```
feat: ✨ #12 エフェクト切替機能を追加する
fix: 🐛 #34 再生中にエフェクト変更すると音が途切れる問題を修正する
docs: 📝 READMEにインストール手順を追記する
refactor: ♻️ #56 AudioEngine クラスのメソッドを整理する
```

### 1.2 Type 一覧

| Type | 説明 | 用途の例 |
|------|------|----------|
| `feat` | ユーザー向けの機能の追加や変更 | 新しいエフェクトの追加、UI変更 |
| `fix` | ユーザー向けの不具合の修正 | バグ修正、クラッシュ対応 |
| `docs` | ドキュメントの更新 | README更新、コメント追加 |
| `style` | フォーマットなどのスタイルに関する修正 | コード整形、空白の調整 |
| `refactor` | リファクタリングを目的とした修正 | コード構造の改善（機能変更なし） |
| `test` | テストコードの追加や修正 | 単体テスト追加、テストデータ変更 |
| `chore` | タスクファイルなどプロダクションに影響のない修正 | .gitignore更新、CI設定変更、依存関係更新 |

### 1.3 Subject（変更内容）のルール

- **現在形** で記述する（「◯◯した」ではなく「◯◯する」）
- 文字数は **20〜30文字以内** を目安とする
- 変更内容が具体的に分かるように書く

#### 良い例 ✅

```
feat: プレイリスト一覧の並び替え機能を追加する
fix: WAVファイル読み込み時のNullReferenceExceptionを修正する
refactor: エフェクト処理のパイプラインを共通化する
```

#### 悪い例 ❌

```
fix: バグを修正する          ← 何のバグか分からない
feat: 機能追加               ← 何の機能か分からない
refactor: リファクタリングする  ← 何を改善したか分からない
```

### 1.4 Description（詳細説明）

- 任意ですが、変更の意図（Why）を補足したい場合は記述します
- WhyはIssueやPull Requestで記載し、コミットメッセージにはIssue番号を紐付ける方針とします

```
feat: #12 エフェクト切替機能を追加する

リアルタイムプレビュー中にエフェクトを切り替えられるようにする。
AudioEngineのパイプラインを動的に組み替える方式で実装。
```

## 3. コミットの粒度

- コミットの粒度は **対応内容（機能・修正）ごとに細かく分ける** ことを基本とします。
- 1つのコミットに **複数の種類の変更を混ぜない** ようにしてください。
  - ❌ 悪い例：「ログ出力を追加し、UIのバグを修正し、さらに新機能を追加した」という1つの巨大なコミット
  - ✅ 良い例：「ログ出力を追加」「UIのバグを修正」「新機能を追加」という3つの独立したコミット
- 1行ごとに細かすぎるコミットにする必要はありませんが、**レビュアーがコミット一覧を見たときに変更の「ストーリー」や「意図」が明確に分かる** 粒度を意識してください。
- PR (Pull Request) を作成する際は、レビューしやすいように意味のある単位でコミットが分割されていることを確認してください。

## 4. その他のルール

### 4.1 Merge / Revert コミット

- Merge CommitやRevert Commitは本フォーマットに従う必要はありません
- Git のデフォルトメッセージをそのまま使用して構いません

### 4.2 .gitignore の管理

以下のファイル・ディレクトリは Git の追跡対象外とします：

```
# ビルド成果物
bin/
obj/
publish/

# ログ・一時ファイル
*.log
*.txt
*.user
.vs/
*.pdb

# ビルド出力
Release_*/

# DocFX 生成物
_site/
api/
docs/
docfx.json
index.md
toc.yml

# その他
objects.txt
```

### 4.3 コミット前の確認事項

1. `git status` で意図しないファイルが含まれていないか確認する
2. `git diff` で変更内容を確認する
3. ビルドが通ることを確認する
4. コミットメッセージがフォーマットに沿っているか確認する

## 5. クイックリファレンス

```bash
# 基本的なコミットの流れ
git add <ファイル>
git commit -m "feat: #12 プレイリスト一覧の並び替え機能を追加する"

# Type 早見表
# feat:     機能追加・変更
# fix:      バグ修正
# docs:     ドキュメント更新
# style:    コード整形
# refactor: リファクタリング
# test:     テスト追加・修正
# chore:    設定・メンテナンス
```
